# 島旅フェリー予約 — 共通フェリー予約プロトタイプ

GitHub Pagesでは `.github/workflows/pages.yml` が `dist` を自動公開します。

伊平屋島・伊是名島の2航路を共通UIで扱う、モバイル優先の操作可能プロトタイプです。すべてデモであり、本物の決済・予約登録・個人情報保存・メール送信は行いません。

## 実装画面

- 利用者画面（`#user`）：島選択トップ、海・雲・波・フェリまるのアニメーション
- 本日の運航状況／今日のフェリー運航イメージ
- 8ステップ予約フロー（往復、日付、便、人数、乗船者、確認、デモ決済、完了）
- QR乗船券、便変更、キャンセル
- 職員管理画面（`#admin`）：専用ヘッダー、権限表示、全航路／伊平屋／伊是名の切替
- 管理ダッシュボード：本日の予約、乗船予定、売上、運航状況、便別人数、最近の予約

プロトタイプではURLフラグで分離しています。本番では管理画面を認証・職員権限で保護し、一般利用者からアクセスできない別ルートまたは別サブドメインとして配備します。

## UIデザイン

- 実写調の沖縄の海と白いフェリーを主役にした旅行サービス風ヒーロー
- 白いカード、濃いブルーの主要ボタン、緑の運航ステータスを基調とした構成
- PCでは横長の島選択パネル、スマートフォンでは写真付きリストへ切り替わるレスポンシブ設計
- 予約画面は1ステップ1タスクで、参考イメージに近い細い進捗バーとカード選択UI
- ヒーロー画像は画像生成機能で作成したプロジェクト専用素材（`dist/assets/okinawa-ferry-hero.png`）

## レスポンシブ検証

- 主な原因：PC用グリッドを狭い画面へ圧縮していたこと、ヘッダー操作が常時横並びだったこと、セクションごとに左右余白が異なっていたこと
- 修正箇所：`dist/index.html` のモバイルメニュー、`dist/app.js` のメニュー制御、`dist/styles.css` のカード・フォーム・QR・管理画面
- スマホ対応：safe-area付き共通ガター、縦型島カード、48px以上の主要操作、16px入力文字、下部操作部、内部スクロール表
- 検証幅：320 / 360 / 375 / 390 / 412 / 430 / 768 / 1280px
- Playwrightによる計測で、利用者画面・予約画面・管理画面のページ全体に横スクロールがないことを確認

## 運航情報の取得

`src/services/ferryStatusService.js` に `FerryStatusService` を定義し、`getIheyaStatus()` と `getIzenaStatus()` を同じ `getStatus(routeId)` に集約しています。本番ではブラウザから村公式サイトへ直接アクセスせず、`/api/ferry-status` のサーバー側アダプターから正規化済みJSONを取得します。サーバー側で公式発表を取得・検証し、失敗時はUIに取得失敗と公式リンクを表示する想定です。

## デモ／実データ切替

```js
new FerryStatusService({ mode: 'demo' })
new FerryStatusService({ mode: 'live', endpoint: '/api/ferry-status' })
```

現在の配信版は完全静的なため、画面表示は `dist/app.js` の航路マスタ内デモデータを使用します。

## 本番化に必要な作業

1. 伊平屋村・伊是名村とデータ利用／取得頻度／障害時表示を合意する

## 予約・在庫の本番設計

配信中のプロトタイプでは便ごとに旅客の定員・予約数・残席と、車両枠の上限・使用数を別々に表示します。決済画面の「仮確保」はUIデモです。本番では `InventoryService` をサーバー側に実装し、`createHold → confirmHold` または `releaseHold` の状態遷移を持たせます。

- 同時予約はDBトランザクション内の行ロックまたは楽観ロックで処理し、`reserved + held + requested <= capacity` を原子的に検証
- リクエストには冪等キーを付け、二重決済・二重予約を防止
- 仮確保には有効期限を持たせ、決済失敗・タイムアウト時に解除
- 旅客席と車両枠を別在庫にし、将来は車種別の必要スペース単位を管理
- `changeDeadlineMinutes` と `cancelDeadlineMinutes` は航路設定として管理

## 状態・例外・通知

定義例は `src/services/reservationDomain.js` に集約しています。予約は予約済み／決済済み／乗船済み／キャンセル／欠航／ノーショー、QRは未使用／乗船済み／キャンセル済み／欠航／期限切れを管理します。QR読取は署名を検証し、同一トランザクション内で一度だけ「乗船済み」へ更新します。

運航側都合の欠航は、`欠航 → 返金対象判定 → 決済事業者へ返金依頼 → 返金処理中 → 返金完了` とし、自己都合キャンセルと理由・規約・監査ログを分離します。通知はメールを最初のチャネルとし、通知イベントと配信チャネルを分けて将来のLINE等へ拡張します。

## 管理・セキュリティ設計

- 権限：システム管理者、伊平屋管理者、伊是名管理者、港担当者、閲覧者
- 管理機能：重要アラート、便別在庫、欠航操作、予約検索、予約詳細、乗船確認、通知履歴、CSV、集計
- 本番対策：HTTPS、管理者認証、サーバー側権限検証、CSRF／XSS／SQLインジェクション対策、API認証、レート制限、操作・監査ログ
- 個人情報は目的・保存期間・閲覧権限を限定。カード情報は保存せず、PCI DSSに準拠する決済事業者へ委譲
- 外部連携は決済、通知、運航情報、観光・交通ごとにアダプター境界を設け、特定事業者への依存を隔離

## UI・アクセシビリティ・通信障害

スマートフォン最優先で、主要操作は48px以上、色に加えて記号と文字を併用し、予約は1画面1タスクにしています。本番では読み込み中、取得失敗、再読み込み、メンテナンスの各画面状態を持たせます。運航情報を取得できない場合は「最新の運航情報を取得できませんでした」と公式サイトへの導線を表示し、取得済み情報には必ず更新日時を表示します。日本語／Englishは翻訳キーと辞書に分離し、画面文言をテンプレートへ直接固定しない方針です。

## 実装優先順位

最優先は島選択、本日の運航、次便、予約、便別定員、QR、スマホUIです。次に管理画面、欠航・返金、通知、CSV、集計を実装します。車両予約、多言語、観光・MaaS連携は、先行機能の運用確認後に拡張します。

## 現行仕様準拠

伊平屋村営フェリーのオンライン予約購入案内（2026-10-30確認）を根拠にした項目です。

- 旅客乗船券のオンライン予約購入と事前決済
- 購入可能日は翌日から30日先まで
- 復路は往路の翌日以降
- 通常ダイヤ：運天発 11:00／15:00、前泊発 09:00／13:00
- 大人 片道2,480円・往復4,720円、小人 片道1,240円・往復2,360円
- 伊平屋村環境協力税は村外からの入域者1名につき100円（例外条件は要確認）
- 自己都合キャンセル処理手数料は乗船者1名につき200円
- クレジットカード、Apple Pay、Google Payによる事前決済
- 出航10分前までの乗船案内
- 障がい者割・団体割・車両予約は窓口へ問い合わせ

通常時刻表 `ScheduledTimetable` と、当日の公式発表 `CurrentOperationStatus` は別データとして扱います。予約枠の「予約可能」と公式の「運航予定」も別状態です。
